# Garmin Planner

Turns the athlete's goals into a rolling plan and keeps the Google Calendar in step with it. The plan is a **draft that adapts**: it is rebuilt weekly from fresh Garmin data, readiness, the run gate, the load check and injuries.

## Always first
1. `python -X utf8 "<skills>/rampwise/scripts/athlete.py" show` (goals, gate, injuries, schedule, HR ceilings). Obey every active injury restriction. If `injury_history_known` is false, ask once about injuries and niggles before planning heavier work, then record the answer with `athlete.py injury-add ...` or `injury-none`.
2. Never invent a date or a timeline for a goal: no verified source gives a rate of improvement for this athlete. Targets are checked, not promised.

## The goals and how they are tested
Goals are whatever the user records in `athlete.json` (`athlete.py goal-add`); the planner never assumes one. Typical goal types and the scripts that measure them:
| Goal type | Measured by | Script |
|---|---|---|
| Aerobic base: hold a pace with HR under the easy ceiling for longer | HOLD minutes, speed at the easy HR, drift (continuous running only) | `rampwise-aerobic-base/scripts/hold_check.py` |
| An optional run gate the user sets (for example a whole session of a given length run with no walking; it locks sessions only if `preferences.quality.requires_gate` is true) | walking found from FIT cadence | `run_gate.py [--record]` |
| A race or pace target (a distance and a time) | a short time trial -> `paces.py predict` / `zones` (rampwise) | `paces.py` |
| A ride speed goal (a target speed over a target distance on a flat route) | flat rides' moving speed, best by distance band, speed per heartbeat | `ride_check.py`, `cycling_power.py` |
| Longer events (a marathon, an ultra ride) | later; need the base, the shorter goals and a long-run/ride build | stored in `athlete.json`, no date |

Use the user's own words for sessions (for example "easy run", never a label the user dislikes) and ask if you are unsure.

## Workflow
1. **State**: run `rampwise-recovery` readiness (`readiness_check.py --brief`) and `load_check.py` (or take the head coach's handoff blocks). Run `run_gate.py --record` (about a minute; it downloads recent run files).
2. **Build**: `python -X utf8 "<skills>/rampwise-planner/scripts/build_plan.py" --start YYYY-MM-DD --weeks 4 --readiness green|amber|red --out "<skills>/rampwise-planner/plans/plan-YYYY-MM-DD.json"`. It reads history from Garmin, applies the rules below, and prints the weeks. Gate state is read from `athlete.json`; override with `--gate passed|open`.
3. **Explain** in phone-friendly form: phase (base or pace intro), why a reset week if one is used, this week's sessions, one thing to watch. Quote numbers only from the script.
4. **Calendar** (main session only, not a subagent): `calendar_events.py PLAN.json --json` prepares event payloads for the next 14 days. Before writing: list events in the window with the connector (`list_events`, `fullText` = `rampwise-plan`), delete old coach events (`delete_event`, notificationLevel NONE), look for clashes with the athlete's own events and tell them, then `create_event` for each, on the primary calendar, no attendees. Report how many were created and how to remove them (search `[GC]`).
5. **Weekly re-sync**: every week (or when the athlete says they were ill, injured, travelled or tired) rebuild from the new data, replace the window, and record the decision with `athlete.py note`.

## Heart-rate targets: zone first, custom second, ask before assuming
Rules (set by the athlete 2026-11-16; they apply to every user):
1. **Ask first.** If `athlete.json` has no `hr.easy_band` (and no legacy `hr.run_easy_max`), `build_plan.py` stops with exit code 2 and prints the questions. Ask the user: do they want to share their watch zones (max HR, LTHR, resting HR, which method: %max, %HRR or %LTHR; a screenshot of the zones page works) and what they call "easy". Record it with `athlete.py set hr.easy_band '{"run":[lo,hi],"bike":[lo,hi]}'` and `athlete.py set hr.zone_sets '{"run":{"method":"..","floors":[z1..z5],"top":MAX},"bike":{..}}'`. Never assume zones.
2. **Zone first.** For each step the builder checks whether ONE zone of that sport's set covers the band (both ends within `hr.target_mode.tolerance_bpm`, default 3). If yes the step uses the watch's own zone ("HR Zone 2 (126-147 bpm on your watch)"); if not it uses a custom bpm range. Every session text says which: "Zone targets (...) use your watch's ... zones" or "Custom bpm (...): your ... zones do not cover this band." `hr.target_mode.prefer = "custom"` turns zones off.
3. **No answer? Use the trend.** `build_plan.py --hr-from-trend` estimates an easy band from the user's own last 60 days (median average HR of steady sessions >= 30 min as the ceiling, 20 bpm below as the floor; needs 5 sessions per sport). Custom bpm only, never zones, printed as an ESTIMATE, not saved to `athlete.json`; ask the user to confirm later (practice, no paper).
4. **Warm-up and cool-down have no HR alert** (open target; the cap is in the step note), so ranges never overlap the main step. Hard efforts (tempo, intervals, climbs) use `hr.hard_band`, `preferences.quality.tempo.hr_low/hr_high` and `preferences.climb.hr_band` when the user has them; without a band the step is open and says "a few words at a time".
5b. **Where the LTHR / max HR came from matters.** Ask whether the LTHR is a watch estimate (auto-detect or guided test, which per Garmin's manual and the Heiber 2024 study needs a chest strap), a lab or lactate test, or a typed guess, and store it in `hr.inputs.lthr_source` / `max_source`. A watch LTHR is an estimate: in one study (Lu 2025, Forerunner 265, n = 23) it was off by about 11 bpm on average, and only 65 % of tests gave a value; another (Heiber 2024, Fenix 7, n = 26) was close on average (-1.7 %) but with a narrower spread than the field test. Label zones built on it as estimated, never as validated, and do not use a typed or default max HR that the athlete has never reached (fixed %max anchors with an estimated max were less accurate in 165 recreational runners, Eur J Appl Physiol 2025). No lab is needed to plan: the talk test and the athlete's own easy band are the practical checks. See `references/evidence-map.md` and `references/library.md` rows 20-24.
5. **Zone targets resolve on the watch**, using the zone set currently on the watch for that sport (running, cycling and the default set are separate and can use different methods). So `hr.zone_sets` must match the watch; if the user changes the method or inputs, re-record it and rebuild. Never put one user's zones, bands or sizes in the scripts.

## Garmin workouts and the session menu
Every run and ride is built as a structured Garmin workout (`scripts/workout.py`): warm-up, steady / interval / tempo, rest or recovery, cool-down, repeat blocks, each step with a duration (time, distance or lap button) and a target (a watch heart-rate zone when one covers the band, otherwise a custom bpm range, pace, speed, cadence, or none). `export_workouts.py PLAN.json` writes one `.fit` file per cardio session (folder: `athlete.json` -> `workouts.output_dir`, default `~/garmin-workouts`) and every file is decoded again as a check. **Not tried on a real watch**: Garmin does not state name limits or loading rules; the usual route is USB -> `GARMIN/NewFiles` (reports are mixed), so say that. Strength sessions are text only.
Session menu (every size and heart-rate band is a setting in `athlete.json`, with common defaults when the user has none): **easy run** (warm-up + steady zone-2 block + cool-down, sizes from `preferences.easy_run`), **long run**, **short run**; an optional **MAF-style test** (a fixed heart rate and equal laps on the same course, settings in `tests.maf`; it replaces a deload-week long run; not gated); **tempo run** (warm-up + a steady block at a hard-but-controlled effort + cool-down); **interval run** (short hard repeats with rests); **strides**; a **3 km time trial**; **climb ride** (a total-ascent target reached by repeating a short climb, `preferences.climb`; the advice on which bike comes from `preferences.climb.bike_hint`). **Quality sessions are ON by default for everyone** (tempo, strides, 3 km time trial, interval run, ride intervals): the Run A slot of each build week rotates through them (order: `preferences.quality.rotation`) and they replace an easy session, so they add no volume. They are locked **per athlete, from that athlete's own data**: (1) an injury with status `active` in `athlete.json` locks them and freezes volume (status `monitoring` only adds the restriction text, `resolved` does nothing); (2) the reset week (RED readiness, 14 days without rest, a load jump) has no quality; (3) `preferences.quality.locked` = types the athlete turned off; (4) `preferences.quality.requires_gate` = true adds the athlete's own no-walking rule as a lock; (5) `preferences.quality.unlocked` = types allowed despite a lock (the athlete's own call). Previews of every type are always written to `workouts/after-gate`. Today's readiness never blocks future weeks: every session says "RED morning: swap for rest". If a quality session hurts, set it with `athlete.py set preferences.quality.locked '["tempo"]'` for that athlete only. Every calendar event carries WHY IT MATTERS (with an evidence label), the watch steps, CHECK AFTER and SAFETY (`scripts/why.py`).

## Plan rules (what the builder does; full table in `references/evidence-map.md`)
- **Base first**: most cardio is easy (HR ceiling from `athlete.json`, talk test); quality is a small share of the week.
- **Quality by default**: from the second week on, one run quality session per build week (rotation of tempo, strides, 3 km time trial, interval run) and one short-interval ride per build week, unless this athlete's data locks them (see the session menu). High-intensity time stays <= 20 % of the week.
- **Volume**: start from the average of the last three full weeks; reset week x0.70 when readiness is RED/AMBER, there was no rest day for 14 days, last week jumped > 20 %, or an injury is active; then at most +10 % per build week; every 4th week x0.75.
- **Long run/ride**: at most +10 % over the longest in the last 30 days, chained week to week (run rule from Frandsen 2025; applied to rides as an extrapolation).
- **Strength equipment** comes from `athlete.json` `equipment.tags`; nothing else is assumed. Banned exercises (`constraints.no_exercises`) are never prescribed (`build_plan.py` refuses to output them). With light loads, lower-body work uses single-leg versions, slow lowering, pauses and band tension (practice; may give a smaller effect than the heavy-strength trials).
- **Strength is generated** (`rampwise-strength/scripts/strength_plan.py`, called by `build_plan.py`): goal profile (`preferences.strength.goal`) + equipment tags + constraints + the user's own Garmin set history. Sizes: `short` 3 moves (default), `mid` 4, `full` all; `max_minutes` trims sets first; sessions per week and weekdays follow the profile (`preferences.strength.days`). Starting weights the history cannot give are printed as `ASK THE ATHLETE (strength)`: ask, do not guess. See the rampwise-strength skill for the 11 goal profiles and their evidence.
- **Strength placement**: on `preferences.strength.days`, at least 3 h after cardio, no heavy lower-body work within 18 h before a key session (practice), lighter in a reset week or when readiness is not GREEN.
- **Schedule** comes from `preferences` (days per week, rest day, long-run and long-ride days, cardio and strength slots). Defaults: 6 days a week, morning cardio, evening strength, long sessions not back to back.
- **Daily override**: each calendar item says "if readiness is RED, swap for rest or a 20-30 min easy spin". The head coach applies it each morning.

## Bikes and rides (athlete.json `equipment.bikes`, `bike_log`, the ride goal)
- A **ride speed goal** (for example a speed over a distance on a flat route) is a goal with `target_speed_kmh`, `target_distance_km`, `flat_max_m_per_km` (flat = at most that many metres of climbing per km; a practice cut-off), `long_ride_km` and optional `baseline`. `ride_check.py` reads it.
- **Which bike a ride used:** Garmin's server does not say. `athlete.json` `bike_log` decides: `{"default_bike": "road", "other_bikes": {"mtb": [activity ids]}}`; a ride counts as the default bike unless its id is listed under another bike. `ride_check.py --bike NAME|all` and `hold_check.py --sport bike --bike NAME|all` use the same log.
- `gearing.py` converts cadence and gear to speed (wheel size assumed unless given); on a fixed gear you cannot coast, so do not plan recovery or descents on it (practice; no paper read).
- The power model (`cycling_power.py`) uses assumed CdA, mass and rolling resistance: the model form is validated (Martin 1998), the numbers are not measurements of the user.

## Honesty rules
- Practice rules (volume steps, reset/deload factors, exercise lists, interval formats, the 125 steps/min walking cut-off, the flat-route cut-off of 8 m/km) are labelled practice. The 10 % weekly rule is **not** shown to prevent injury (Buist 2008); it is a conservative convention.
- Speed numbers from rides depend on wind, stops and traffic; use them as context. The power model uses assumed CdA, mass and rolling resistance; the model form is validated (Martin 1998), the numbers are not measurements of the athlete.
- If a signal is missing (no readiness, no gate check), build the plan with the safer assumption (readiness RED, gate open) and say so.
- A coach is not a doctor: pain that changes gait or worsens, chest pain, fainting -> stop and see a clinician.
